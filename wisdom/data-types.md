# Data type reference

Cross-problem reference: when to use each data type, common alternatives, and the gotchas that produce real production incidents. Consult when designing schemas (§7) or modeling external API payloads.

The general principle: **use the most expressive type for the data.** Stuffing everything into `VARCHAR` loses every guarantee the DB could enforce.

---

## Numeric

| Type | Size | When to use |
|---|---|---|
| `SMALLINT` (`int2`) | 2 B | Small enums or bounded counters (HTTP status codes, day-of-week). Rarely worth it on big tables. |
| `INT` / `INTEGER` (`int4`) | 4 B | Generic integers when you're confident the value won't exceed ~2.1 billion. |
| **`BIGINT` (`int8`)** | **8 B** | **Default for primary keys, foreign keys, and counters on growing tables.** 4-byte overflow is a real production incident pattern (Twitter's tweet ID, YouTube's view count). |
| `DECIMAL(p,s)` / `NUMERIC` | variable | **Money. Always. Never use FLOAT for money.** Floats can't represent `$0.10` exactly → rounding losses compound over millions of transactions. |
| `FLOAT` / `REAL` (4 B) / `DOUBLE PRECISION` (8 B) | 4–8 B | Genuine measurements where small rounding is acceptable: scientific data, ML features, geo distances. |

**Rule:** for IDs and counters, default to `BIGINT`. The 4-byte savings of `INT` aren't worth the migration pain when you exhaust 2 billion.

---

## Strings

| Type | When to use |
|---|---|
| `VARCHAR(n)` | Variable-length strings with a known max. Length cap should match the **API contract** (e.g., alias ≤ 32 → `VARCHAR(32)`), not be guessed. |
| `TEXT` | Variable-length strings without a meaningful max (descriptions, comments, blog body). In **Postgres**, `VARCHAR(n)` and `TEXT` are stored identically; in **MySQL**, `TEXT` is stored off-row and can't be fully indexed → prefer `VARCHAR(n)` in MySQL. |
| `CHAR(n)` | Fixed-length, padded with spaces. Almost never useful in modern systems. **Exception:** fixed-length hashes / UUIDs *if* you're not using a binary type. |

**Gotchas:**

- A `VARCHAR(n)` length is in **characters**, not bytes. UTF-8 takes 1–4 bytes per char → `VARCHAR(2048)` can hold up to ~8 KB on disk.
- Indexing very long strings is expensive — consider hashing the column and indexing the hash for equality lookups.
- **Case sensitivity**: emails, usernames, codes → decide explicitly. Postgres is case-sensitive by default; either store lowercased or use `CITEXT` / expression indexes. Same content with different casing must compare equal where the product expects it to.

## Datetime — the type most candidates get wrong

| Type | Stores | When to use |
|---|---|---|
| **`TIMESTAMPTZ`** (`TIMESTAMP WITH TIME ZONE`) | A point in time, normalized to UTC, returned in client's session zone | **Default for any global / multi-region service.** Eliminates DST and timezone bugs at the data layer. |
| `TIMESTAMP` (without time zone) | A wall-clock string, no timezone awareness | Use when the wall clock matters more than the absolute moment (e.g., "send report at 09:00 in the user's local time"). Rare. |
| `DATE` | Calendar date, no time | Birthdays, holidays, financial reporting periods. |
| `TIME` | Time of day, no date | Rare. Schedules, store hours. |
| `INTERVAL` | A duration | Durations between events; TTL offsets. |

**Common datetime gotchas:**

- **Storing as `INT` epoch seconds**: tempting but loses semantics — DB tools can't filter "this month" without conversion. Use the native type unless you have a specific reason.
- **Naive `TIMESTAMP` (no zone) in a global service is a bug factory.** Two users in different zones see "2026-05-04 14:00" and mean different absolute moments. DST is worse — clocks jump forward or backward, and a naive timestamp can't represent the ambiguous hour.
- **Resolution mismatch**: Postgres stores microseconds, JS `Date` is milliseconds, Unix is seconds. Round-tripping through different layers can cause `==` checks to fail. Decide on the precision boundary at the API.
- **Always store in UTC, render in user's zone.** This is non-negotiable for global services.

## UUIDs

| Approach | Size | Notes |
|---|---|---|
| **`UUID` (binary)** | 16 B | Native type in Postgres / many engines. Fastest comparison, smallest. **Default if available.** |
| `CHAR(36)` (string form `xxxxxxxx-xxxx-...`) | 36 B | Use only if your DB lacks a native UUID type. ~2.25× the storage. |
| Auto-increment `BIGINT` | 8 B | Smaller, faster, but generated by the DB — bad fit for distributed systems where you want IDs minted before insert. |

**UUID variant matters for index health:**

- **UUIDv4 (random)** — every insert hits a different page in the B-tree → fragmented index, worse cache locality, slower inserts on huge tables.
- **UUIDv7 (timestamp-prefixed, standardized 2024)** — newer inserts go to the same end of the index → behaves like an auto-increment for index purposes. **Prefer UUIDv7 over v4 for distributed-system PKs.**

## Other types worth knowing

| Type | When to use | Common alternative gone wrong |
|---|---|---|
| `BOOLEAN` | True/false flags | Don't store as `CHAR(1)` `'Y'`/`'N'` or `TINYINT(1)` — loses semantics, breaks tooling |
| `JSONB` (Postgres) | Genuinely schemaless data, third-party payloads, audit logs | Don't use as a dumping ground for fields that should be normalized columns — querying gets ugly fast |
| `INET` / `CIDR` (Postgres) | IP addresses | Storing IPs as `VARCHAR(15)` breaks CIDR-range queries and numeric sorting |
| `BYTEA` / `BLOB` | Small binary data (hashes, encrypted blobs) | Don't store large binaries (images, videos) in DB — use object storage (S3) and store the URL |
| Enum (DB-level) | Bounded value sets | DB enum changes require migration. CHECK constraint with string is more flexible. Pure app-level validation is easier still. Use DB enum only when DB-level integrity matters. |

## Cross-cutting principles

1. **Pick the smallest type that fits — but with margin.** At 100M rows, 4 vs 8 bytes per row = 400 MB difference + index size. But don't pick `INT` over `BIGINT` to save a few GB if there's any chance of overflow.
2. **API contract length = DB column length.** They should match. Different sizes are an integrity hole — DB rejects what API accepted, or vice versa.
3. **Indexes inherit the column's size.** Wide columns make wide indexes. A `VARCHAR(2048)` PK is a much worse idea than a `VARCHAR(32)` PK.
4. **Default to `NOT NULL` unless NULL is meaningful.** NULL has three-valued-logic semantics that break naive queries (`WHERE x = NULL` always returns false; `WHERE x != 'foo'` excludes NULLs).
5. **Use the most expressive type for the data.** UUID column for UUIDs, INET for IPs, JSONB for JSON. Stuffing everything into VARCHAR loses every guarantee the DB could enforce.
6. **At storage scale, type choice compounds.** A 1-byte column saving × 1 B rows = 1 GB on disk + 1 GB in indexes + 1 GB in replicas + 1 GB in backups. Type discipline matters.

---

## Top 5 gotchas to internalize

1. **`FLOAT` for money** → rounding errors, lost cents. **Always `DECIMAL` / `NUMERIC`.**
2. **Naive `TIMESTAMP` in a global service** → DST bugs, off-by-an-hour incidents. **Always `TIMESTAMPTZ`.**
3. **`INT` primary key on a fast-growing table** → multi-day migration when you exhaust 2.1 B. **Default to `BIGINT`.**
4. **`UUID` as `VARCHAR(36)`** → ~2.25× storage, slower compares. **Use the binary UUID type.**
5. **Storing IPs as strings** → can't query CIDR ranges, can't sort numerically. **Use `INET` / `BIGINT`.**
